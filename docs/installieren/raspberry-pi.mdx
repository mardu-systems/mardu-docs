---
title: Server auf dem Raspberry Pi installieren
description: Mardu aus privaten GitHub-Container-Images installieren und mit Docker Compose aktualisieren.
---

Das Paket startet API, Dashboard, Datenbank und HTTPS-Proxy auf dem Pi mit fertigen
Images aus der GitHub Container Registry (GHCR). Ein lokaler Build ist nicht nötig.

## Voraussetzungen

- Raspberry Pi mit einem 64-Bit-Linux-System und ausreichend Speicher für API,
  Dashboard und TimescaleDB. Eine Kapazitätsprüfung für deine Installation bleibt
  erforderlich.
- Docker Engine und aktuelles Docker Compose v2 sowie `openssl` und `tar`.
- Berechtigung, Docker mit deinem Linux-Benutzer auszuführen. Verwende für Login
  und Compose denselben Benutzer. Bei Ausführung mit `sudo` braucht auch der
  Root-Benutzer einen eigenen Registry-Login.
- Eine Domain, die auf den Pi zeigt. Für die automatische öffentliche
  Zertifikatsausstellung durch Caddy müssen Port 80 und 443 erreichbar sein.
  Die Anleitung setzt diese HTTPS-Betriebsform voraus; eine reine LAN-IP reicht
  dafür nicht aus.
- Lesezugriff auf die privaten GHCR-Pakete `mardu-rpi-api` und `web` in der
  Organisation `mardu-systems` sowie auf das Backend-Repository für den Download
  der Release-Anhänge.
- Einen aus dem API-Container erreichbaren externen IP500-MQTT-Broker und dessen
  Verbindungsdaten. Der Einrichtungsassistent setzt diese Verbindung voraus.

## 1. Installationspaket herunterladen

Lade `mardu-raspberry-pi.tar.gz` aus einem freigegebenen GitHub-Release von
`mardu-systems/mardu-rpi-api` und übertrage das Paket auf den Pi.

Entpacke das Archiv in einen eigenen, dauerhaft verwendeten Installationsordner:

```bash
mkdir -p ~/mardu
tar -xzf mardu-raspberry-pi.tar.gz -C ~/mardu
cd ~/mardu
```

Der Ordner enthält `compose.yaml`, `Caddyfile` und `.env.example`. Behalte den
Ordnernamen bei: Compose leitet daraus standardmäßig die Namen der Datenvolumes
ab. Ein anderer Projektname verwendet andere Volumes.

## 2. Zugang zu privaten Images einrichten

Erstelle in deinem GitHub-Konto einen Personal Access Token **classic** mit
`read:packages`. Das Konto muss beide Pakete lesen dürfen. Falls die Organisation
SSO verlangt, autorisiere den Token dafür. Ein Fine-grained Token ersetzt den
klassischen Token für diesen GHCR-Login nicht.

Melde dich auf dem Pi an:

```bash
docker login ghcr.io -u DEIN_GITHUB_BENUTZERNAME
```

Ersetze den Benutzernamen und gib den Token in der verdeckten Passwortabfrage ein.
Docker speichert ihn für diesen Linux-Benutzer. Schütze diesen Zugang; der Token
gehört weder in `compose.yaml` noch in `.env`.

## 3. Installation konfigurieren

```bash
umask 077
cp .env.example .env
chmod 600 .env
openssl rand -hex 32
openssl rand -hex 32
```

Öffne `.env` mit einem Texteditor. Setze `DOMAIN` auf deine Domain ohne `https://`.
Verwende die beiden unterschiedlichen Zufallswerte für `NEXTAUTH_SECRET` und
`POSTGRES_PASSWORD`. Lass die beiden Image-Tags auf `stable`, um freigegebene
Updates beim nächsten Startbefehl zu übernehmen.

Compose setzt aus `DOMAIN` auch `AuthBroker:PublicBaseUrl` am API-Server. OIDC-Callbacks
verwenden dadurch die öffentliche HTTPS-Adresse, während das Dashboard intern weiter
`http://server:8080` verwendet. Bei einem getrennten API-Host oder Pfadpräfix kannst
du `AuthBroker__PublicBaseUrl=https://api.example.com/server` in `.env` ergänzen;
die Proxy-Routen müssen dann zu dieser Adresse passen. Siehe
[OIDC-Anmeldung einrichten](../administration/oidc-anmeldung.mdx).

Bewahre `.env` auf. Ändere das Datenbankpasswort einer bestehenden Installation
nicht nur in dieser Datei: PostgreSQL übernimmt diese Variable nur bei der
erstmaligen Initialisierung eines leeren Datenvolumes.

## 4. Starten und einrichten

```bash
docker compose config --quiet
docker compose up -d
docker compose ps
```

Warte, bis `db`, `server` und `web` als gesund (`healthy`) angezeigt werden.
Lies danach den Setup-Token aus:

```bash
docker compose exec server cat /app/Private/setup-token.txt
```

Der Token autorisiert die Ersteinrichtung; er ist kein Anmeldepasswort. Gib ihn
nicht weiter. Nach erfolgreichem Setup wird die Token-Datei gelöscht.

**Bekannte Einschränkung des Erstsetups:** Im geprüften Quellstand verwendet
Production-Compose intern Port `8080`, der Assistent übermittelt `5001`. Die
Validierung lehnt den Konflikt ab und verhindert den Setup-Abschluss. Prüfe vorab,
ob dein Release ihn behebt; gesunde Container allein bestätigen das nicht.

Der Einrichtungsablauf für eine Version ohne diesen Konflikt:

1. Öffne `https://DEINE-DOMAIN/standalone/setup`, trage den Token unter
   **Setup-Token** ein und wähle **Autorisieren**. Die folgende **Systemprüfung**
   muss erfolgreich sein.
2. Trage unter **PostgreSQL verbinden** Host `db`, Port `5432`, Datenbank `mardu`,
   Benutzer `postgres` und das `POSTGRES_PASSWORD` aus `.env` ein. Ersetze das
   vorausgefüllte Passwort durch deinen erzeugten Wert. Falls du Datenbank oder
   Benutzer in `.env` geändert hast, verwende diese Werte. Wähle **Datenbank
   testen** und gehe nach erfolgreicher Prüfung weiter.
3. Fülle **Projekt und Administrator einrichten** aus. Verwende unter **Origin
   der Administrationsoberfläche** `https://DEINE-DOMAIN` ohne Pfad. Lege das erste
   lokale Administratorkonto mit Vorname, Nachname, E-Mail-Adresse und einem
   eigenen Passwort mit mindestens 16 Zeichen an; zusätzliche Serverrichtlinien
   werden bei der Validierung geprüft. Die E-Mail-Adresse ist der Benutzername.
   Bewahre das Passwort auf: Es gibt kein gemeinsames Standardkonto für diese
   Installation.
4. Trage unter **IP500 über MQTT verbinden** die Adresse und Zugangsdaten des
   externen Brokers ein. `localhost` bezeichnet hier den API-Container, nicht den
   Pi oder einen anderen Rechner. Wähle **Verbindung testen**. Wähle danach nur
   benötigte **Optionale Integrationen** und entscheide über die angebotene
   Fehlerberichterstattung.
5. Wähle unter **Prüfen und anwenden** zuerst **Konfiguration validieren**. Behebe
   gemeldete Fehler, bevor du **Setup anwenden** wählst.

Beim Anwenden startet die API neu, initialisiert die Datenbank und legt den
Administrator an. Warte auf den erfolgreichen Abschluss und melde dich mit dem
angelegten Konto unter `https://DEINE-DOMAIN/standalone/auth` an. Prüfe außerdem
`https://DEINE-DOMAIN/health/ready`: Während der Ersteinrichtung antwortet dieser
Endpunkt mit HTTP `503`; erst danach dient er als Bereitschaftsprüfung.

Intern verwenden API, Dashboard und Datenbank die Ports `8080`, `3000` und
`5432`; der Browser greift über Caddy auf HTTPS-Port `443` zu. Der
Container-Healthcheck nutzt `/health/live`, auch vor der Datenbankinitialisierung.

Konfiguration, Dateien, private Schlüssel, Zertifikate und Datenbank liegen in
Docker-Volumes und bleiben bei einem Containerwechsel erhalten. Der Stack
veröffentlicht zusätzlich MQTT-Ports `1883` und `8883`; der eingebettete Broker
muss bei Bedarf samt Authentifizierung und TLS eingerichtet werden. Der angepasste
Node-RED-Dienst gehört nicht zu diesem Paket und benötigt für Automationen eine
separate Bereitstellung.

## 5. Neue Versionen übernehmen

Sichere vor einem Update die Datenbank und die persistenten Volumes. Die API kann
beim Start Datenbankmigrationen ausführen. Ein Rückwechsel des Image-Tags allein
stellt einen früheren Datenbankstand nicht wieder her. Lies vorher die Hinweise
des Ziel-Releases zur Datenbankkompatibilität.

Führe im gleichen Installationsordner aus:

```bash
docker compose up -d
docker compose ps
```

Der Befehl prüft die `stable`-Images und ersetzt geänderte Container; dabei kann
die Anwendung kurz ausfallen. Vorabversionen aktualisieren `stable` nicht. Updates
laufen nur bei diesem Aufruf, nicht im Hintergrund. Prüfe danach `/health/ready`.

Die Compose-Datei selbst wird dadurch nicht heruntergeladen. Verlangt ein Release
neue Dienste oder Einstellungen, übernimm die zugehörigen Installationsdateien
aus dessen Anhang und behalte deine `.env` und den Installationsordner bei.
`docker compose down -v` löscht die Datenvolumes; verwende es nicht für Updates.

Für eine festgelegte Version setze `API_IMAGE_TAG` und `WEB_IMAGE_TAG` in `.env`
auf die jeweils passenden Release-Tags. Solange die Tags festgelegt sind, folgt
die Installation nicht `stable`.

## Probleme beheben

- `unauthorized` oder `denied`: Prüfe Paketberechtigungen, Token-Ablauf, SSO und
  den verwendeten Linux-Benutzer. Wiederhole `docker login ghcr.io`.
- `manifest unknown`: Für den angegebenen Tag wurde noch kein Image veröffentlicht.
  Vor der ersten Installation müssen API und Dashboard jeweils einen erfolgreichen
  Release mit `stable` besitzen.
- HTTPS funktioniert nicht: Prüfe Domain, DNS und Erreichbarkeit von Port 80/443
  sowie `docker compose logs proxy`.
- Setup oder API startet nicht: Prüfe `docker compose logs server db`. Ein
  erfolgreicher Liveness-Check ersetzt nach dem Setup keine Readiness-Prüfung.

Die Token- und Paketregeln beschreibt die
[GitHub-Dokumentation zur Container Registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).
