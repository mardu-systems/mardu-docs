---
title: HTTPS-Zertifikatswechsel vorbereiten und prüfen
description: Die zuständige HTTPS-Komponente bestimmen, ein direktes API-Zertifikat wechseln und die verwendete Verbindung prüfen.
---

Der Browser kann ein anderes Zertifikat empfangen als das unter
**Server → Server-Zertifikate** gespeicherte.

Du brauchst die Dashboard- und API-Adressen der bestehenden Installation sowie
für Listener- oder Proxyänderungen Host- und Deployment-Zugriff. Im Dashboard
benötigt die Zertifikatsliste `Settings.View`, Upload, Ersetzen und Löschen
benötigen `Settings.Update`.

## 1. Zuständige Komponente bestimmen

Notiere die vollständige betroffene Adresse einschließlich Hostname und Port.
Unterscheide die im Browser geöffnete Dashboard-Adresse von einer separat
angesprochenen API-Adresse.

| Verwendung                               | Woher kommt das Zertifikat?                                                                                  | Wo erfolgt die Änderung?                                                             |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| Direkter HTTPS-Zugriff auf die API       | Der API-Webserver Kestrel lädt die konfigurierte Zertifikatsdatei.                                           | In der Listener- und Dateikonfiguration des API-Deployments.                         |
| HTTPS im Raspberry-Pi-Installationspaket | Der vorgeschaltete Proxy Caddy nimmt HTTPS auf Port `443` an; die API verwendet intern HTTP auf Port `8080`. | Am bestehenden Proxy-Deployment.                                                     |
| Zertifikat unter **Server-Zertifikate**  | Der Mardu-Zertifikatsspeicher stellt Material für zugeordnete Integrationen wie LDAP, OIDC oder MQTT bereit. | Im Speicher und in der jeweiligen Integration; dies ändert den HTTPS-Listener nicht. |

Für andere Proxys gilt deren Konfiguration; ein API-Neustart wechselt ihr
Zertifikat nicht. Die Betriebsform des Installationspakets erklärt
[Raspberry Pi installieren → Installieren](../installieren/raspberry-pi.mdx).

## 2. Wechsel vorbereiten

Prüfe Gültigkeit, Hostnamen, Zertifikatskette und passenden privaten Schlüssel.
Kläre betroffene Verbindungen, plane die Unterbrechung bei einem API-Neustart und
halte den bisherigen funktionsfähigen Konfigurationsstand zur Wiederherstellung bereit.

Soll nur ein gespeichertes Integrationszertifikat ersetzt werden, folge
[Servereinstellungen → Ersetzen oder löschen](./server-einstellungen.mdx#ersetzen-oder-löschen).
Die Zertifikats-ID bleibt beim Ersetzen erhalten. Prüfe danach die zugeordnete
Integration nach [Integrationen](./integrationen.mdx). Ein CA-Zertifikat, mit dem
Mardu einen LDAP- oder OIDC-Server prüft, erteilt dem Browser kein Vertrauen in
die Mardu-Adresse.

### Direktes API-Zertifikat wechseln

Diese Schritte gelten nur für direktes HTTPS über Kestrel, nicht für das
Caddy-Installationspaket.

1. Prüfe im bestehenden Deployment, ob `KestrelOptions__EnableHttps` aktiv ist,
   welcher `KestrelOptions__HttpsPort` verwendet wird und wie dieser Port
   erreichbar ist. Der voreingestellte HTTPS-Port ist `7443`; eine
   Container-Portfreigabe ist davon getrennt.
2. Stelle das neue Zertifikat mit privatem Schlüssel als PFX-/P12-Datei so bereit,
   dass der API-Prozess sie lesen kann. Setze
   `Kestrel__Certificates__Default__Path` auf diesen Dateipfad und, falls nötig,
   `Kestrel__Certificates__Default__Password` über die Geheimnisverwaltung des
   Deployments. In einem Container gilt der Pfad im Container. Relative Pfade
   beziehen sich auf das Inhaltsstammverzeichnis (Content Root) der API.
3. Übernimm Datei- und Konfigurationsänderungen im Deployment und starte die API
   neu: Der Listener lädt das Zertifikat beim Start. Geänderte Container-
   Umgebungsvariablen erfordern auch die Übernahme der Containerkonfiguration.
4. Prüfe die tatsächliche HTTPS-Verbindung nach dem folgenden Abschnitt.

Das vorhandene lokale Overlay `docker-compose.https.yml` bindet ein Zertifikatsverzeichnis
unter `/certs` schreibgeschützt ein und veröffentlicht den Containerport `7443`.
Verwende bei dieser Betriebsform den Pfad innerhalb dieses Mounts. Die
Zertifikats-ID aus dem Dashboard ist kein Dateipfad für Kestrel.

Ist HTTPS eingeschaltet und kein Zertifikatsdateipfad konfiguriert, verwendet die
API ein dauerhaft gespeichertes, selbstsigniertes Ersatz-Zertifikat. Das ist kein
Nachweis für Browservertrauen oder einen passenden öffentlichen Hostnamen.

## 3. Verwendete Verbindung prüfen

1. Öffne die tatsächlich genutzte HTTPS-Adresse erneut und kontrolliere in den
   Verbindungsinformationen des Browsers das ausgelieferte Zertifikat. Vergleiche
   Fingerabdruck, Gültigkeit und Hostname mit dem vorgesehenen Zertifikat.
2. Prüfe, ob der Browser die Zertifikatskette akzeptiert.
   **Selbstsigniertes Zertifikat zulassen** im Uploaddialog installiert kein
   Vertrauen auf Endgeräten. Kläre dies mit der für die Geräte zuständigen Person.
3. Wird die API über eine eigene Adresse angesprochen, prüfe auch deren
   Zertifikat. Ein gültiges Dashboard-Zertifikat bestätigt die getrennte
   API-Verbindung nicht.
4. Prüfe eine neue Anmeldung und die betroffene Funktion. Ergänzend hilft die
   [Zustandsprüfung](./sicherheit-betrieb.mdx#eine-störung-eingrenzen).
   Ein erreichbarer Health-Endpunkt allein bestätigt keinen funktionierenden
   Anmelde- oder Integrationsablauf.

## Wenn die Verbindung nicht funktioniert

| Beobachtung                                                               | Nächste Prüfung                                                                                                                                                                       |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Der Browser zeigt weiterhin das bisherige Zertifikat.                     | Prüfe die genaue Adresse und den Port sowie die zuständige Komponente. Bei direktem Kestrel-Zugriff prüfe Dateipfad und API-Neustart; bei vorgeschaltetem Proxy dessen Konfiguration. |
| Die API startet nach dem Wechsel nicht.                                   | Prüfe Startprotokoll, Dateipfad im laufenden Deployment, Leserechte, privates Schlüsselmaterial und Dateipasswort. Stelle bei Bedarf den zuvor geprüften Stand wieder her.            |
| Der Browser meldet einen falschen Namen, Ablauf oder fehlendes Vertrauen. | Prüfe den aufgerufenen Hostnamen, Gültigkeitszeitraum, Gerätesystemzeit und Zertifikatskette. Ein erneuter Upload in den Mardu-Speicher behebt Clientvertrauen nicht.                 |
| Nach dem Speicherwechsel scheitert nur LDAP, OIDC oder MQTT.              | Prüfe die Zertifikatszuordnung und Verbindung im betroffenen Integrationsbereich. Unterscheide das CA-Vertrauen einer ausgehenden Verbindung vom Serverzertifikat eines Listeners.    |
